# Серверный персонаж

Один Telegram ID из проверенного сервером `initData` соответствует одной строке `character_saves`. Клиент получает персонажа через `GET /api/game`; создание доступно только после подтверждённого отсутствия персонажа. ID из тела запроса не выбирает владельца.

## Источники данных

| Сущность | Источник |
| --- | --- |
| Персонаж, игровая валюта, добыча, навыки, квесты, достижения, профессии | `character_saves.state_json` |
| Предметы существующего серверного реестра | `owned_items`; исключаются из JSON сохранения |
| Рыночный кошелёк, Premium, принадлежность к клану | Существующие серверные таблицы |
| Язык, звук, интерфейс | Хранилище устройства |

Общие правила находятся в `src/game/GameModel.ts`. Production-провайдер отправляет именованные команды, сервер выполняет правила в транзакции. Постоянного API загрузки произвольного клиентского персонажа нет. Старые HTTP-мутации предметов, рынка, клана, PvP и `/api/profile/sync` закрыты для обхода командного протокола. `LocalGameProvider` служит только явной тестовой фикстурой.

## Версии, сессии, повторные запросы

Команда передаёт `expectedVersion`, `sessionId`, `sessionGeneration` и UUID `operationId`. Сервер блокирует строку аккаунта и сохранения; состояние, изменения `owned_items` и квитанция фиксируются одной транзакцией. Повтор возвращает ранее зафиксированный результат. Повтор с другими параметрами отклоняется.

Второе устройство получает актуального персонажа, но для изменений требуется кнопка «Играть на этом устройстве». Перенос увеличивает поколение сессии. Старые команды блокируются; при конфликте клиент загружает актуальное состояние и останавливает действия. Поздний ответ чтения не заменяет новую подтверждённую версию.

До отправки команда записывается в отдельный ключ устройства. Потерянный ответ и перезапуск документа повторяют тот же UUID. Подтверждённый кеш разделён по Telegram ID и проверяется по владельцу и `reset_version`. Потеря сети блокирует действия и показывает возможность повтора. Сохранение не зависит от закрытия страницы.

## Бой и путешествие

Сервер хранит здоровье и ману обеих сторон, раунд, эффекты, использованные зелья, фазу хода, запланированный удар, цепочку боёв и награды. Путешествие хранит время прибытия и выбранную засаду; энергия списывается при старте. Следующая команда возобновляет таймеры из подтверждённого состояния. Чтение не выдаёт награды. Закрытие приложения не возвращает потраченные ресурсы.

Старое локальное сохранение не содержит полного состояния обычного боя. Незавершённый старый поход при миграции закрывается без наград и возврата энергии, со штрафом отступления; исходный снимок сохраняется отдельно. Неподтверждённые локальные сюжетные встречи удаляются.

## Миграция и развёртывание

SQL: `server/migrations/20261007_server_characters.sql`; те же определения включены в существующий стартовый `server/schema.sql`. Перед развёртыванием сделайте резервную копию PostgreSQL и обновите сервер и клиент совместно: старый клиент больше не сохраняет прогресс старым протоколом.

Миграция создаёт таблицы сохранений, квитанций и резервных снимков, но не придумывает персонажей из неполного `players.level`. Однократно записанный `game_schema_migrations.applied_at` открывает окно переноса на 30 дней; рестарт его не продлевает.

Если найден старый локальный персонаж, игрок явно выбирает его перенос, серверного персонажа или создание нового. Проверяются структура, владелец, эпоха сброса и диапазоны значений. Резервная копия исходного снимка сохраняется на устройстве и сервере до переноса; перед заменой сохраняется также серверный снимок. Валюта, предметы и награды разных персонажей не суммируются. Существующие `owned_items` остаются каноническими и не копируются повторно из локального JSON.

Разрешены один первичный импорт и одно явное разрешение конфликта с другим старым персонажем в том же ограниченном окне. Повторная загрузка состояния уже перенесённого персонажа запрещена. После явной замены или истечения окна импорт закрыт. Это позволяет выбрать различающиеся старые персонажи двух устройств без постоянного API перезаписи прогресса.

Административный сброс очищает персонажа, увеличивает версию и поколение сессии и закрывает миграцию. Сохранения и квитанции старой эпохи не восстанавливают удалённый прогресс.

## Проверки и границы

Результат финального прогона:

| Проверка | Результат |
| --- | --- |
| `npm run lint` | TypeScript без ошибок |
| `npm test` | 217/217 успешно |
| `npm run check:interfaces` | Сборка и проверка production-модулей успешно |

Vite сообщает о существующем крупном чанке локализации; Node предупреждает об экспериментальном VM Modules API в тестовом скрипте. Это не ошибки проверок. Скорость загрузки и задержки серверного API не измерялись.

Интеграционные проверки используют реальный Express HTTP, подписанный Telegram `initData`, production-провайдер в JSDOM, настоящие SQL-запросы в PGlite и реальные обработчики предметов. Покрыты два устройства, перенос сессии, версии, повтор/потеря ответа, перезапуск, разные аккаунты, миграция, сброс, восстановление боя и путешествия, откат транзакции и задержанный ответ чтения.

Production-проверка исполняет выпущенные JS-модули и проверяет три интерфейса, разделы и шесть направлений переключения. Это не проверка физического телефона, Telegram WebView или реального Network браузера. Миграция на действующей БД и нагрузочный прогон многопроцессного PostgreSQL в этой среде не выполнялись. Резервные снимки и квитанции пока хранятся без автоматической очистки; политика архивирования должна сохранять защиту повторов.
